Business Central Webhooks: Complete Practical Guide

Dynexal • Beginner to Intermediate • 14 min read

Webhooks let an external application receive notifications when a Business Central entity changes. Instead of repeatedly polling an API, your integration can subscribe to a resource and react when Business Central sends a notification.

What you will learn: webhook architecture, subscriptions, validation handshakes, notification payloads, clientState, renewals, custom APIs, retries, security, testing and production integration patterns.

What is a webhook?

A webhook is a server-to-server notification pattern. An external application provides a public HTTPS notificationUrl, creates a subscription for a Business Central resource, and then receives notifications when the subscribed entity changes.

This is different from polling. With polling, your application repeatedly asks Business Central whether anything changed. With a webhook, Business Central calls your endpoint when a change notification is available.

Simple idea: API polling asks, “Did anything change?” A webhook lets Business Central tell you, “Something changed.”

Why use Business Central webhooks?

  • Reduce unnecessary repeated API requests.
  • React to changes with lower integration latency.
  • Build event-driven integrations between Business Central and external systems.
  • Keep e-commerce, CRM, warehouse and middleware systems more synchronized.
  • Use standard APIs or supported custom API resources as webhook sources.

Webhook architecture

A typical Business Central webhook flow looks like this:

  1. Your application exposes an HTTPS notification endpoint.
  2. Your application calls the Business Central subscriptions endpoint.
  3. Business Central sends a validation request containing a validationToken.
  4. Your endpoint returns the token with HTTP 200 OK.
  5. The subscription becomes active.
  6. When the subscribed entity changes, Business Central sends a notification to your endpoint.
  7. Your application processes the notification and, when needed, calls the Business Central API to retrieve the current record.

The validation handshake is mandatory when creating and renewing subscriptions. The subscriber must return the validation token in the response body with status code 200. citehttps://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-connect-apps-delta

Create a webhook subscription

For the standard Business Central API, the subscription endpoint is based on the Business Central API URL. A simplified request looks like this:

POST https://{businesscentralPrefix}/api/v2.0/subscriptions
Content-Type: application/json

{
  "notificationUrl": "https://example.com/api/business-central/webhook",
  "resource": "/api/v2.0/companies({companyId})/customers",
  "clientState": "your-shared-state-value"
}

The current Microsoft documentation uses the v2.0 subscriptions API and shows notificationUrl, resource and optional clientState in the request body. citehttps://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/api/dynamics_subscriptions_create

The validation handshake

When Business Central creates or renews a subscription, it first validates that your notification endpoint can receive webhook calls. Business Central sends a request to your notification URL with a validationToken query parameter.

Your endpoint must return that token in the response body and use HTTP status 200 OK.

HTTP/1.1 200 OK
Content-Type: text/plain

{validationToken}
Common mistake: returning JSON such as {"token":"..."} when the handshake expects the validation token in the response body. Implement the handshake exactly as required by the Business Central webhook contract.

Example webhook endpoint

The following pseudocode shows the important logic. The exact implementation depends on your server technology.

POST /api/business-central/webhook?validationToken=abc123

if validationToken exists:
    return 200 OK
    body = validationToken

otherwise:
    read notification body
    verify clientState
    queue notification for processing
    return 200 OK

For production systems, keep the HTTP endpoint fast. Receive and validate the request, place work on a durable queue when appropriate, and process business logic asynchronously.

What does a webhook notification contain?

A notification identifies the resource that changed and includes information needed by the subscriber to decide what to do next. The notification can contain a clientState value when one was supplied during subscription creation or renewal.

Do not assume that the webhook payload is a complete replacement for reading the resource. A common integration pattern is to use the notification as a trigger and then call the relevant Business Central API endpoint to retrieve the current entity.

Using clientState for verification

clientState can be used as an opaque value or shared secret that the subscriber checks when receiving notifications. Microsoft documents clientState as a value delivered with notifications and suitable for helping the subscriber verify messages or manage state. citehttps://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-connect-apps-delta

Expected clientState:
BC-DYNEXAL-SECRET-123

Received notification:
clientState = BC-DYNEXAL-SECRET-123

Result:
Process notification
Security note: never hard-code real production secrets into source code or publish them in tutorials, repositories or client-side JavaScript. Use a secure secret store or environment configuration in a real application.

Webhook subscriptions expire

Business Central webhook subscriptions are not permanent. Microsoft documents that subscriptions expire after three days if they are not renewed. Renewal is performed with a PATCH request to the subscription resource, and renewal also requires the validation handshake. citehttps://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-connect-apps-delta

PATCH https://{businesscentralPrefix}/api/v2.0/subscriptions({subscriptionId})
Content-Type: application/json

{
  "notificationUrl": "https://example.com/api/business-central/webhook"
}

The subscription response includes an expirationDateTime property. Your integration should store the subscription ID and expiration time and renew it before it expires.

Get existing subscriptions

You can retrieve subscription information through the Business Central subscriptions resource. Current v2.0 documentation supports GET, POST, PATCH and DELETE operations for subscription management. citehttps://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_subscriptions

GET https://{businesscentralPrefix}/api/v2.0/subscriptions

Use the returned subscription information to monitor active subscriptions and their expiration dates.

Delete a webhook subscription

When an integration is removed or a resource no longer needs monitoring, delete the subscription instead of leaving unused subscriptions active.

DELETE https://{businesscentralPrefix}/api/v2.0/subscriptions({subscriptionId})

Subscription management includes creating, reading, updating and deleting subscriptions. citehttps://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_subscriptions

Webhooks with custom API pages

Custom API pages can also be used with Business Central webhooks. When subscribing to a custom API, the subscription URL and resource path must use the same APIPublisher, APIGroup and APIVersion values defined by the custom API.

api/{publisher}/{group}/{version}/subscriptions

For example, if a custom API uses publisher dynexal, group integration and version v1.0, the subscription route follows that API namespace.

This makes webhooks particularly useful when a standard API does not expose exactly the business entity your integration needs. citehttps://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-connect-apps-delta

Webhook notifications are not the same as AL events

AL events such as IntegrationEvent and EventSubscriber are primarily an internal Business Central extension mechanism. Webhooks are an external integration mechanism that sends HTTP notifications to another application.

FeatureAL EventsWebhooks
Main purposeInternal extension logicExternal notifications
Typical consumerAL subscriber codeExternal HTTP service
TransportAL runtimeHTTPS

Webhooks vs polling

Polling can be simpler for a first prototype, but frequent polling can create unnecessary API traffic and still leaves a delay between changes and detection. Webhooks are better suited when you want Business Central to notify your application when supported resources change.

A practical architecture can combine both approaches: use webhooks for fast change detection and a scheduled reconciliation process to recover from outages or missed processing.

Handling duplicate notifications

Production integrations should be designed to tolerate repeated or delayed notifications. Do not assume that one HTTP request always maps to exactly one business operation.

  • Persist a notification or resource identifier when appropriate.
  • Make downstream processing idempotent.
  • Use queues for durable processing.
  • Log failures and retry safely.
  • Periodically reconcile important data with the source system.

Retry and endpoint availability

Your webhook endpoint should be reliable and reachable over HTTPS. Microsoft documents retry behavior when Business Central cannot reach the subscriber. The documented retry-related responses include 408, 429 and 5xx responses; other response codes can cause retries not to continue and can lead to the subscription being deleted. citehttps://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v1.0/dynamics_subscriptions

Because of this, avoid returning arbitrary error codes when a temporary failure occurs. Handle transient failures deliberately and monitor your endpoint.

Real-world e-commerce example

Imagine a Shopify-to-Business-Central integration with an external middleware service:

  1. Business Central customer data changes.
  2. The webhook sends a notification to the middleware.
  3. The middleware validates the notification.
  4. The middleware retrieves the latest customer through the Business Central API.
  5. The middleware transforms the data for the external system.
  6. The middleware updates the external platform.
  7. The middleware records the processing result for audit and troubleshooting.

The webhook acts as the trigger; the API provides the current resource data; the middleware handles transformation and business workflow.

Testing a webhook integration

  1. Expose a temporary HTTPS endpoint in a controlled development environment.
  2. Create the Business Central subscription.
  3. Confirm that the validation handshake succeeds.
  4. Change a supported entity in Business Central.
  5. Check that the notification reaches your endpoint.
  6. Verify the clientState value if you use one.
  7. Retrieve the current resource through the API.
  8. Test temporary endpoint failures and retry behavior.
  9. Test subscription renewal before expiration.
  10. Test deletion and recreation of a subscription.

Common webhook problems

1. Subscription creation fails

Check the subscription URL, authentication, resource path and notification URL. Also verify that your endpoint correctly handles the validation handshake.

2. Validation token is not accepted

Make sure the endpoint returns the validation token in the response body with HTTP 200 and does not wrap it in an unrelated JSON structure.

3. Notifications are not arriving

Check that the subscription is active, the resource is supported, the endpoint is publicly reachable over HTTPS, and the subscription has not expired.

4. Subscription suddenly stops working

Check expirationDateTime and your renewal process. A subscription that is not renewed can expire after three days.

5. Your integration processes the same change twice

Design processing to be idempotent and keep an appropriate processing record or key.

6. Your endpoint becomes overloaded

Return quickly, queue work, apply back-pressure and avoid performing long-running business logic directly in the webhook request.

Production best practices

  • Use HTTPS for notification endpoints.
  • Validate the Business Central webhook handshake correctly.
  • Use clientState as part of your notification verification strategy.
  • Store subscription IDs and expiration timestamps securely.
  • Renew subscriptions before expiration.
  • Make processing idempotent.
  • Use durable queues for important integrations.
  • Log subscription creation, renewal, notification receipt and processing failures.
  • Use least-privilege authentication for API access.
  • Keep webhook endpoints fast and resilient.
  • Add reconciliation jobs for critical data flows.
  • Never expose secrets in browser code or public repositories.

Frequently asked questions

Do Business Central webhooks replace APIs?

No. Webhooks notify your application that something changed. Your application can then use the Business Central API to retrieve or modify the resource.

Do webhooks work with custom APIs?

Yes. Business Central supports webhook subscriptions for custom API pages when the custom API and subscription paths are configured correctly.

How long does a webhook subscription last?

Microsoft documents a three-day expiration period when a subscription is not renewed. Your integration should renew it before expiration.

Can I use webhooks with customers and sales orders?

Supported Business Central API resources can be subscribed to. Always verify the current supported-resource list for your Business Central version and API surface.

Should I process the whole business operation inside the webhook request?

Usually no. For reliable production integrations, acknowledge the notification quickly and process longer work asynchronously.
