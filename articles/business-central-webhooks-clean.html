Business Central Webhooks: Complete Practical Guide

Dynexal • Beginner to Intermediate • 14 min read

Webhooks let an external application receive notifications when a Business Central entity changes. Instead of repeatedly polling an API, your integration can subscribe to a resource and react when Business Central sends a notification.

What you will learn: webhook architecture, subscriptions, validation handshakes, notifications, clientState, renewals, custom APIs, retries, security, testing and production patterns.

What is a webhook?

A webhook is a server-to-server notification pattern. An external application provides a public HTTPS notificationUrl, creates a subscription for a Business Central resource, and then receives notifications when that resource changes.

Polling repeatedly asks Business Central whether something changed. A webhook lets Business Central notify your endpoint when a supported entity changes.

Simple idea: polling asks, “Did anything change?” A webhook lets Business Central tell you, “Something changed.”

Why use Business Central webhooks?

  • Reduce unnecessary repeated API requests.
  • React to changes with lower integration latency.
  • Build event-driven integrations with CRM, e-commerce, warehouse and middleware systems.
  • Use a notification as a trigger and retrieve current data through the Business Central API.

Webhook architecture

  1. Your application exposes an HTTPS notification endpoint.
  2. Your application creates a Business Central webhook subscription.
  3. Business Central sends a validation request containing a validationToken.
  4. Your endpoint returns that token with HTTP 200 OK.
  5. The subscription becomes active.
  6. When the subscribed entity changes, Business Central sends a notification.
  7. Your application validates and queues the notification, then retrieves current resource data when needed.

Create a webhook subscription

A standard v2.0 subscription request can look like this:

POST https://{businesscentralPrefix}/api/v2.0/subscriptions
Content-Type: application/json

{
  "notificationUrl": "https://example.com/api/business-central/webhook",
  "resource": "/api/v2.0/companies({companyId})/customers",
  "clientState": "your-shared-state-value"
}

The request identifies the notification endpoint, the Business Central resource and optionally a client state value.

The validation handshake

When Business Central creates or renews a subscription, it validates that your endpoint can receive webhook calls. The request includes a validationToken query parameter.

HTTP/1.1 200 OK
Content-Type: text/plain

{validationToken}
Common mistake: returning an unrelated JSON object instead of the exact validation token in the response body with HTTP 200.

Example endpoint logic

POST /api/business-central/webhook?validationToken=abc123

if validationToken exists:
    return 200 OK
    body = validationToken

otherwise:
    read notification
    verify clientState
    queue notification
    return 200 OK

Keep the webhook endpoint fast. For production systems, validate the request, put important work on a durable queue and process business logic asynchronously.

What does a webhook notification do?

A webhook notification tells the subscriber that a subscribed resource changed. Treat it as a trigger rather than assuming it contains every current field value. A common pattern is webhook → validate → Business Central API → retrieve current record → process integration.

Using clientState

clientState is delivered with notifications when supplied during subscription creation or renewal. It can be used as an opaque value or shared secret that the subscriber checks before processing a notification.

Expected clientState:
BC-DYNEXAL-SECRET-123

Received:
BC-DYNEXAL-SECRET-123

Result:
Process notification
Security: never publish real production secrets in source code, tutorials, repositories or client-side JavaScript. Use secure configuration or a secret store.

Webhook subscriptions expire

Business Central webhook subscriptions are temporary. Microsoft documents a three-day expiration period when a subscription is not renewed. Renewal uses PATCH and also requires the validation handshake.

PATCH https://{businesscentralPrefix}/api/v2.0/subscriptions({subscriptionId})
Content-Type: application/json

{
  "notificationUrl": "https://example.com/api/business-central/webhook"
}

Store the subscription ID and expirationDateTime and renew before expiration.

Get and delete subscriptions

GET https://{businesscentralPrefix}/api/v2.0/subscriptions

DELETE https://{businesscentralPrefix}/api/v2.0/subscriptions({subscriptionId})

Subscription management supports reading, creating, updating and deleting subscriptions.

Webhooks with custom API pages

Custom API pages can also be webhook-enabled. The subscription URL and resource path use the same APIPublisher, APIGroup and APIVersion values as the custom API.

api/{publisher}/{group}/{version}/subscriptions

This is useful when a standard API does not expose exactly the business entity your integration needs.

Webhooks vs AL events

AL events such as IntegrationEvent and EventSubscriber are mainly an internal Business Central extension mechanism. Webhooks are an external HTTP integration mechanism.

FeatureAL EventsWebhooks
PurposeInternal extension logicExternal notifications
ConsumerAL subscriberExternal HTTP service
TransportAL runtimeHTTPS

Webhooks vs polling

Polling can be useful for simple prototypes, but frequent polling creates repeated API traffic and detection delay. Webhooks are better when you want Business Central to notify an external system about supported resource changes.

A robust architecture can combine both: webhooks provide fast change detection while a scheduled reconciliation job recovers from outages or missed processing.

Handling duplicate notifications

Production integrations should tolerate repeated or delayed notifications. Design processing to be idempotent.

  • Persist a useful notification or resource identifier.
  • Make downstream operations safe to repeat.
  • Use a durable queue.
  • Log failures and retry safely.
  • Run periodic reconciliation for critical data.

Retry and endpoint availability

Your notification endpoint should be publicly reachable over HTTPS and return appropriate HTTP responses. Business Central documents retry behavior for temporary subscriber failures, including 408, 429 and 5xx responses. Monitor the endpoint and avoid returning arbitrary errors for transient problems.

Real-world e-commerce example

  1. A Business Central customer or order changes.
  2. Business Central sends a webhook notification to middleware.
  3. The middleware validates the request.
  4. The middleware retrieves the latest record through the Business Central API.
  5. The middleware transforms the data.
  6. The external e-commerce or CRM system is updated.
  7. The processing result is logged.

Testing a webhook integration

  1. Expose a controlled HTTPS endpoint.
  2. Create the Business Central subscription.
  3. Confirm the validation handshake succeeds.
  4. Change a supported entity.
  5. Confirm the notification arrives.
  6. Verify clientState if used.
  7. Retrieve the current entity through the API.
  8. Test temporary endpoint failures.
  9. Test renewal before expiration.
  10. Test deletion and recreation.

Common problems and fixes

Subscription creation fails

Check the API URL, authentication, resource path, notification URL and validation handshake.

Validation token is rejected

Return the exact token in the response body with HTTP 200.

No notifications arrive

Check that the subscription is active, the resource is supported, the endpoint is reachable over HTTPS and the subscription has not expired.

Subscription stops after a few days

Check expirationDateTime and implement automatic renewal.

Same change is processed twice

Make processing idempotent and maintain a suitable processing record.

Endpoint becomes slow

Return quickly and move long-running work to a queue or background worker.

Production best practices

  • Use HTTPS.
  • Implement the validation handshake exactly.
  • Validate clientState where appropriate.
  • Store subscription IDs and expiration timestamps.
  • Renew subscriptions before expiration.
  • Use idempotent processing.
  • Use durable queues for important integrations.
  • Log subscription lifecycle and processing failures.
  • Use least-privilege authentication for API access.
  • Add monitoring and reconciliation for critical data flows.
  • Never expose production secrets in public code.

Frequently asked questions

Do webhooks replace APIs?

No. Webhooks notify your application that something changed. The API can then retrieve or modify the resource.

Do webhooks work with custom APIs?

Yes. Supported custom API pages can be used with webhook subscriptions when the API namespace and subscription route are configured correctly.

How long does a subscription last?

Business Central documents a three-day expiration period when a subscription is not renewed.

Can webhooks be used for customers and sales orders?

Supported API resources can be subscribed to. Always verify the current supported-resource list for your Business Central version.

Should I run long business logic directly in the webhook request?

Usually no. Acknowledge quickly and process longer work asynchronously.
